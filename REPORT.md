## Сборка и запуск

Разные части проекта написаны на разных языках. Стартовый набор - C11, реализация сборщика вместо заглушки - C++23. Все разрабатывалось и тестировалось на ОС Ubuntu 24.04 с компилятороми gcc и g++ 13.3.0, системой сборки CMake 3.28.3. Единственная внешняя зависимость - библиотека `fmt`, котрая лежит в `3dparty` (в cmake используется флаг `-DFMT_HEADER_ONLY`, чтобы сделать ее header-only, никаких дополнительных действий по установке не требуется)

Так как сборщик написан на C++, он состыковывается с данным API путем включения хедера `bridge.hpp`. В `gc.cpp` находятся реализации всех требуемых функций API. Основная реализация находится в `heap.cpp` и `context.hpp`. Чтобы реализация на C++ работала, нужен так же C++ Runtime, для которого необходимы `-lstdc++` и `-lm`. Сборка через CMake из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./build/chat 10 # 45
```

Проект можно также собрать и без средств CMake из корня проекта:

```bash
gcc -std=c11 -Iinclude -I3dparty -DFMT_HEADER_ONLY examples/chat.c runtime/runtime.c runtime/scalar.c runtime/main.c -x c++ -std=c++23 gc.cpp -o chat -lstdc++ -lm
```

Тогда итоговый бинарный файл будет лежать также в корне проекта


Собираются четыре программы с одним рантаймом: `chat`, `double`, `history`, `playlist`. Для того, чтобы добавить другие программы на Си, необходимо изменить CMake (см. функцию foreach в `CMakeLists.txt` в корне проекта)

Тесты (см. раздел "Тестирование"):

```bash
ctest --test-dir build          # or: make -C test/ut check
```

Для воспроизведения нужны те же gcc/g++ 13.x и cmake ≥ 3.20.

## Алгоритм и устройство реализации

Основной алгоритм - копирующая сборка с алгоритмом Чени. Дополнение - инкрементальная сборка (алгоритм Бейкера). Оба параметра конфига (объем работы на шаге, порог начала цикла) поддержаны. Код:

- `include/gc/heap.hpp` - полупространства, аллокация, сборка со всеми шагами (сканирование, форвардинг корней барьеры чтения и т.д.)
- `include/gc/context.hpp` - проверки аргументов ABI, списки корней, статистика, вывод состояния;
- `include/gc/root.hpp`, `include/gc/config.hpp`, `include/gc/utils.hpp` - корни, параметры, размеры объектов;
- `gc.cpp` - реализации функций API

Устройство и инварианты:

- Два полупространства по `max_heap_bytes` байт. В моменты вне сборки объекты укладываются в from-space подряд от начала по адресу `m_next`
- Сборка запускается при пороге занятости (`occupied * 100 >= end * threshold`) или при нехватке места под новый объект. Первым делом форвардятся корни (перманентные и динамические), далее сканируются объекты в очереди Чени в to-space: `[toBegin, toBegin + next)` - живые, но еще не перенесенные объекты переносятся по адресу next и попадают в эту очередь, если объект уже был перенесен, то просто меняется ссылка у managed-поля. В промежутке `[toBegin + limit, toBegin + end)` находятся новые объекты, аллоцированные уже во время сборки (укладываются от конца вниз), между ними свободная зона. Инвариант: `m_scan <= m_next <= m_limit <= m_end`
- Барьер чтения - при чтении managed-поля: `Context::readManaged` вызывает `Heap::forward`, который переносит объект из from-space в to-space и оставляет в `gc_word` обратную ссылку. Если gc_word уже содержит форвард-ссылку, то объект заново не переносится, эта ссылка просто становится новым указателем в managed-поле. Write barrier отсутствует - в алгоритме Бейкера он не предусмотрен, поэтому `write_barrier_activations` всегда 0
- Инкрементальность - на каждую ноавую аллокацию `collectionStep` выполняет не более `scansPerStep` сканирований очереди; сборка считается завершённой, когда `m_scan == m_next`. В этот момент from-space и to-space меняются местами, инкрементируется метрика завершенных сборок
- Нехватка места во время коллекции - `finishWoBudget` досканирует очередь синхронно (инкрементируются метрики количества аллокаций со сканированиями без учета бюджета и количесвто таких сканирований), если и после этого объект не помещается - `stella_gc_out_of_memory`, программа завершается с сообщением "cannot allocate N bytes" и инкрементируется метрика неудачных аллокаций

## Параметры

| Параметр | Смысл | Способ задания | Допустимые значения | По умолчанию |
|---|---|---|---|---|
| `max_heap_bytes` | размер каждого полупространства, байт | второй аргумент запускаемой программы | >= 1 (0 - ошибка "zero-length heap size requested") | 64 MiB |
| `scansPerStep` | бюджет сканирований очереди Чени на одну аллокацию | `STELLA_GC_SCANS_PER_STEP` | >= 1 (0 - ошибка "zero scans per allocation step") | 1 |
| `collectionThreshhold` | занятость кучи в процентах, при которой начинается сборка | `STELLA_GC_COLLECTION_THRESHOLD` | 1…100 (вне диапазона - "collection threshold out of range") | 100 |
| `STELLA_GC_STATS`, `STELLA_GC_STATE` | печатать статистику/состояние в stderr | переменные окружения | как в описании | выключено |

## Тестирование

Тестирование было произведено при помощи unit-тестов на реализованные модули. Этот подход был выбран просто потому, что я привык к нему на работе и он мне нравится. Был сделан ограниченный фреймворк в `test_util.hpp` с макросами `CHECK`, `CHECK_VIOLATION` для проверки нарушений ABI, счётчики проверок. Сборка и запуск: `ctest --test-dir build` (или старый вариант `make -C test/ut check`). Все `CHECK_VIOLATION`-тесты построены на том, что `stella_abi_violation` кидает исключение (для этого была написана отдельная реализация только для тестирования), ловящееся тестовым фреймворком.  Sunny-case тесты проверяют значения статистики и адреса объектов

Показательные тесты:

- `heap.cpp: collection_preserves_reachable_graph` - строит граф, аллокациями доводит хип до коллекции и проверяет, что оба объекта живы, `x` перенесён (`x_new != x_old`), поле `x_new->fields[0]` по-прежнему указывает на `y`
- `context.cpp: read_barrier_forwards_field_during_collection` - во время коллекции читает managed-поле корня: чтение перемещает объект (`y_new != y_old`), `gc_word` старой копии становится адресом новой
- `heap.cpp: scans_per_step_budget_is_configurable` - с `scansPerStep = 3` одна аллокация продвигает очередь не более чем на 3 объекта; счётчик `total_scans` растёт порциями по бюджету
- `heap.cpp: collection_starts_when_threshold_reached` и `threshold_counts_objects_allocated_during_collection` - порог запуска коллекции и учёт объектов, аллоцированных во время коллекции (занятость `next + (end − limit)`); последний проверяет, что такие объекты не теряются и попадают в следующий цикл
- `heap.cpp: oom_when_live_objects_do_not_fit_semispace` - если живое множество больше полупространства, аллокация завершается `stella_gc_out_of_memory`, `failed_allocations` растёт
- `root.cpp` - push/pop в порядке стека, дублирующая регистрация, underflow/out-of-order, очистка при `cleanup()`; `context.cpp` - валидация дескрипторов (kind, флаги, entry code, переполнения), статические объекты, индексы полей; `config.cpp` - чтение и валидация переменных окружения, недопустимые значения.


Каких-то серьезных ошибок, кроме некорректного печатания состояния (печаталось пространство [begin; begin + occupied), а не [begin; next) + [limit; end)), найдено не было. Основные падения проиходили как раз таки из-за тестов. Они подходят скорее в качестве регрессии

Недостаточно проверены длинные стрессовые прогоны с чередованием всех видов операций (чтение/запись/updateObject во время сборки), поведение на границе `SIZE_MAX` для размера кучи.

## Известные ограничения

- Двойной расход памяти: два полупространства по `max_heap_bytes`, допустимо условием
- Во время сборки живое множество должно помещаться в to-space целиком, иначе - OOM
- Так как не все объекты переносятся сразу, фактическая доля живых объектов может быть больше 100% от заданного размера кучи, но когда следующий объект поптается переместиться, OOM завршит выполнение программы 
- Все остальные ограничения алгоритма Бейкера
